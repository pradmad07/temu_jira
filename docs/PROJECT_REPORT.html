Executive Summary

The Intelligent IT Service Management & Incident Resolution System (I-ITSM) is an enterprise-grade incident management platform designed to automate and optimize the handling of IT disruptions in modern enterprise organizations. Built in accordance with ITIL service delivery standards and rigorous Object-Oriented Design principles, the platform guides incidents through an unbroken, legally enforced state lifecycle: Report → Classify → Prioritize → Assign → Investigate → Resolve → Verify → Close.

The system is developed in Python 3.13 using a clean Layered Architecture with FastAPI, Jinja2 / Bootstrap 5, and SQLite 3 accessed strictly through Repository Pattern contracts. It is backed by a 100% green automated test suite of 112 tests.

1. Problem Analysis

Enterprise organizations rely on dozens of interconnected IT services: identity providers, relational databases, cloud APIs, and transaction gateways. Manual incident triage introduces systemic operational failures: delayed initial notifications, arbitrary user-driven priority inflation, overloaded support engineers, missed SLA commitments, and duplicated investigation of common outages.

I-ITSM solves these challenges through algorithmic multi-factor prioritization ($P1–P4$), skill- and load-based automated assignment, a rigid State Pattern lifecycle preventing invalid transitions, continuous non-blocking SLA scanning, and multi-channel notifications (In-App + simulated SMTP).

5. Technology Stack Selection Justification (Answers to the 9 Mandatory Questions)

1. Why did you choose this programming language?

Python 3.13 was chosen for its clean, expressive syntax, formal interface contracts via abc.ABC, strict encapsulation through private variables and @property getters, and native testing and threading support.

2. Why did you choose this frontend technology?

Server-Rendered HTML5 + Jinja2 + Bootstrap 5 was chosen to eliminate fragile build toolchains (npm/webpack) and guarantee that role authorization is enforced on the server before HTML generation, preventing security leakage.

3. Why did you choose this backend technology?

FastAPI provides high-performance asynchronous request handling with a composable Dependency Injection system (Depends()) that enforces RBAC guards declaratively.

4. Why did you select this database?

SQLite 3 is zero-configuration, fully ACID compliant, and embedded in-process. Relational joins and B-tree indexes are encapsulated behind Repository Pattern contracts, allowing zero-code domain changes if swapping to PostgreSQL.

5. Why did you choose this architecture?

A Layered Architecture with an Event-Driven Observer Bus enforces unidirectional dependencies, keeping core business and lifecycle logic isolated from web routers and SQL queries.

6. What alternatives did you consider?

We evaluated React + Express + MongoDB (rejected: document stores lack relational joins required for SLA monitoring) and Django Monolith (rejected: Django ORM tightly couples models to SQL, violating Clean Architecture).

7. What are the advantages and limitations of your technology stack?

Advantages: Instantaneous test runs (112 tests in 38s), zero external server dependencies, deterministic CI runs. Limitations: SQLite single-writer lock (mitigated by fast, granular transactions).

8. How does your technology support object-oriented design?

Python provides native classes, single and multiple inheritance, abstract base classes, property getters, and polymorphism, supporting all 6 implemented GoF design patterns.

9. How would your system evolve if the number of users increased significantly?

1) Swap SQLite for PostgreSQL behind existing repositories; 2) Scale stateless web nodes behind a load balancer; 3) Replace in-memory EventBus with Apache Kafka or RabbitMQ worker pools.

11. Object-Oriented Design & Patterns Defended

1. State Pattern (states.py)

Decouples lifecycle states into distinct classes (NewState, AssignedState, InProgressState, etc.). Illegal transitions are prevented structurally rather than via nested conditional statements.

2. Strategy Pattern (priority.py, assignment.py)

Encapsulates priority scoring and technician assignment algorithms behind common interfaces. The system switches between Skill-Based and Load-Based strategies at runtime without code changes.

3. Observer Pattern (events.py, audit.py)

Decouples core business transactions from side-effects. The EventBus broadcasts domain events to AuditObserver and NotificationService independently.

4. Repository Pattern (interfaces.py, sqlite_repos.py)

Separates domain entities from database access mechanisms. Domain services interact purely with abstract base classes, enabling simple database engine swaps.

5. Factory Pattern (factories.py)

Encapsulates creation and validation of polymorphic user entities (User vs Technician), enforcing secure password hashing and uniqueness rules.

6. Adapter Pattern (notifications.py)

Standardizes heterogeneous notification delivery channels (In-App notifications and simulated SMTP email) behind a uniform NotificationChannel interface.
